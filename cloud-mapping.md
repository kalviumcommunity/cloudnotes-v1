# CloudNotes: Local Deployment to Compute Engine Mapping

| What I built locally | Compute Engine equivalent | Why they play the same role |
|---|---|---|
| Multipass Ubuntu 24.04 VM (in place of VirtualBox / UTM / WSL / Docker) | Compute Engine VM (e2-medium, Ubuntu) | Both provide a full, isolated Linux operating system with a real kernel and systemd; Multipass provisions this on my own Mac's hardware, while Compute Engine provisions the identical OS image on Google's hardware in a datacenter. |
| `multipass shell cloudnotes-vm` | `gcloud compute ssh` | Both open an interactive remote shell session into the Linux server to run commands, install packages, and manage services; `multipass shell` connects over Multipass's internal local transport, while `gcloud compute ssh` connects over the internet using SSH key authentication. |
| `192.168.252.2:5000` (VM's bridged-network IP) | VM static external IP | Both are the network address + port that a client (browser/curl) connects to in order to reach the Flask app; my VM's private bridged IP works because it's on the same local network as my Mac, whereas a Compute Engine VM needs a real, internet-routable static external IP since clients connect from anywhere on the public internet. |
| `ufw allow 5000/tcp` (OS firewall) | GCP VPC firewall rule (tcp:5000) | Both are the access-control layer that must explicitly permit inbound traffic on port 5000 before any request reaches the app; `ufw` enforces this at the OS level inside the VM, while a VPC firewall rule enforces it at the network level before traffic even reaches the VM. |
| systemd (`cloudnotes.service`) | systemd on the VM | This is literally the same technology; Compute Engine VMs running Ubuntu also use systemd, so the exact same `deploy/cloudnotes.service` unit file could be copied onto a Compute Engine VM unchanged and would provide the same start-on-boot and restart-on-crash guarantees. |
| PostgreSQL installed via `apt` on the VM | Cloud SQL (managed, LU 2.7) | Both store CloudNotes data in a real PostgreSQL database that the app talks to via a `DATABASE_URL` connection string; my local PostgreSQL is a process I installed and must personally patch, back up, and keep running, while Cloud SQL is Google's managed PostgreSQL service that handles patching, backups, and high availability automatically. |
| `.env` file (read via `python-dotenv`) | Instance metadata / Secret Manager | Both supply configuration (like `DATABASE_URL` and `SECRET_KEY`) to the app without hardcoding it into source code; locally this is a git-ignored `.env` file loaded at startup, while on Compute Engine the equivalent is either instance metadata (for non-secret config) or Secret Manager (for actual secrets), fetched by the app at startup instead of reading a local file. |

## Summary

Every piece of my local Multipass-based deployment has a direct Compute Engine counterpart: the VM itself, remote shell access, network addressing, firewall rules, the systemd service manager, the PostgreSQL database, and environment-variable-based configuration. The main practical differences when moving to Compute Engine would be replacing self-managed PostgreSQL with Cloud SQL, and replacing the local `.env` file with Secret Manager for the `SECRET_KEY` and database credentials — everything else (the systemd unit file, the Flask/gunicorn app code, the firewall port-opening logic) would transfer over largely unchanged.
